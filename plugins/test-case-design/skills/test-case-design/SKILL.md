# 面向执行人的测试用例设计

参考 ACC、组合测试和通用设计技术，产出可执行、可评审的用例。方法来源不代表 Google、微软认证或满足其未公开的内部标准。保留用户指定范围、格式和优先级约定；项目约定优先于这里的默认规则。

## 首要目标与阅读顺序

让熟悉产品但没参加需求讨论的测试人员，拿到一条用例就能找到入口、准备数据、执行操作并判断结果。结构、标题、前置和步骤的合理性优先于台账丰富度；追踪完整和构建成功不能替代内容质量。

- 新写或改写用例前，必读 [reference/writing-style.md](reference/writing-style.md)，按其中的四项标准和自检问题编写。已有手写样例时，先跨模块抽取有代表性的目录与完整用例，归纳用户写法；只借鉴表达和组织方式，不移植旧业务规则、空前置、模糊预期或复制错误。
- 工作顺序是：理解业务与入口 → 拆规则和覆盖点 → 按功能主线组织并校准目录与短标题 → 写完整代表用例并自审 → 扩展剩余场景 → 双向核对覆盖 → 构建文件。测试点用于检查遗漏，不直接作为目录或标题模板。
- 先写覆盖本次不同形态的少量完整代表例（如列表筛选、编辑字段、状态操作），发现共性问题先修正，再继续批量展开。样例校准是内部工作，不新增用户审批环节；用户主动要求预览时按其要求交付。
- 仅做格式转换时保留原内容与树；需要改写内容时才应用本写作标准。小任务可将覆盖、来源和问题合并进简短评审，不为格式制造空表。

## 菜单归属与资产维护

- 开始设计或调整模块前，读取 [reference/menu-assets.md](reference/menu-assets.md)，建立有来源的菜单清单和归属映射。顶层归属严格对应真实菜单/应用入口路径；菜单下按业务功能、字段、操作或测试主题分组，避免所有用例平铺。功能分组是测试目录，不冒充产品菜单；PRD 文件名和版本号不作为目录。没有完整菜单资料时只使用已证实路径，其余列待确认，不编造菜单。
- 保留“规则 → 原子测试点 → 模型项 → 用例”的设计链路；菜单决定存放位置，Capability 表达能力与影响关系，版本 Test Plan 选择资产，Test Run 记录执行结果，四者不混用。
- 初版设计保持原有测试点拆解流程；已有用例或迭代维护时，先盘点、比较规则、检索旧资产，再按 REUSE / MODIFY / DEPRECATE / ADD / REVIEW 决策，仅对需要新增或修改的部分展开设计。旧用例 ID 与平台真实 ID 分别保留，不能随版本、菜单移动或排序重建。
- 参考文档中的执行提示、示例编号和平台说明是待评估资料，不自动成为用户本次任务；只吸收适用规则，不触发无关批量生成、平台迁移或配置修改。

## 工作流

### 任务启动信息收集

先读取已有需求、范围、入口、历史用例和交付要求。最小输入是“需求依据 + 本次范围”；已经提供的资料不重复询问。缺失信息只提出影响本次设计的具体问题，并继续处理独立明确部分。缺原型时可用 PRD 明确的页面与控件，不发明点击位置、弹窗或按钮名；会影响执行或判断的缺口记入 `review.md`。未知预期不能写进正式可执行集，用户要求的假设草案单列。

1. **确认依据与范围**：盘点实际输入、批准状态、菜单来源、基线版本和已有资产覆盖范围；记录 PRD 版本、章节、验收标准及接口/设计资料。将复合验收标准拆成原子规则，保留原编号；无编号时生成本地规则 ID 并注明来源，不伪造原文编号。区分范围外功能与必须禁止的行为，只有后者必需负向测试。
2. **处理不确定性**：列出缺失、冲突和不可测试规则及问题 ID。错误码、补偿、时限、字符单位、幂等语义等未定义时，不自行补成确定预期。阻塞规则留在待确认清单，不进入可执行交付集；继续设计独立且明确的部分。仅在用户要求草案时给出带假设标记的候选，不混入已确认用例。
3. **先拆测试点**：设计新用例时先读 [reference/test-points.md](reference/test-points.md)，按 PRD 章节、字段表、流程、权限及状态规则逐项拆解，先产出 `test-points.md`，再展开用例。每个测试点分配稳定 `TP-xxx`，关联规则与具体依据，明确一个可独立判定的行为或约束。不可用“验证新增功能”“字段校验”等模块名称代替测试点。已提供测试点时先补齐拆解与追踪；仅构建已有大纲时不强制重做设计。
4. **建模与风险评估**：范围复杂时用 ACC 梳理组件、能力和适用质量属性；小范围用测试点清单即可。按 [reference/methods.md](reference/methods.md) 记录评分、证据、优先级及覆盖目标。边界、异常、UI、多语言均不天然属于某个优先级，不按比例凑数。
5. **逐点展开设计**：为每个测试点列出适用的正向/负向等价类、边界或决策/迁移模型项，给模型项局部编号，逐项关联用例；不适用维度写原因。根据下表读取 methods.md 对应章节。先覆盖各点独立行为，再补有依据的交互和端到端场景。高风险规则不能仅靠成对组合或错误推测覆盖。
6. **编写与追踪**：按已核对菜单路径组织用例；增量场景按 menu-assets.md 记录资产决策和版本计划。生成 `outline.txt`；`test-points.md` 保存测试点及展开项；同目录的 `review.md` 记录依据、问题/假设、范围/风险、规则→测试点→模型项→用例的追踪矩阵、覆盖缺口和剩余风险。用户指定其他载体时保留同等信息。测试点台账建立后直接继续生成用例，不额外要求用户逐点批准；不确定项按步骤2处理。
7. **分级验证与交付**：先内容评审，再严格构建。文件验证通过才能交付文件；未做真实导入时标记“MeterSphere 导入未验证”，不得声称测试已执行或已通过。

## 方法选择

| 规则信号 | 技术与覆盖证据 |
|---|---|
| 需求明确规定字段约束（必填、长度、字符/格式、范围、枚举、唯一性等） | 有效/无效等价类、适用边界点清单；没有明确约束则不单独生成字段校验用例 |
| 多条件、权限 | 判定表、可行规则及拒绝规则 |
| 状态、生命周期 | 状态/事件/守卫条件矩阵，按风险补迁移序列 |
| 用户旅程、多角色 | 主流程、备选流、异常恢复流 |
| 多参数组合 | 带约束的 PICT、可行参数对覆盖，必要时提高阶数 |
| 并发、幂等、依赖故障 | 故障注入与时序场景、触发及观测方式 |
| 范围不清、模块多 | ACC 范围模型 + 风险清单 |
| 未知风险、可用性 | 探索式 charter，未执行时只交付计划 |

## 用例编写

- 用例以一个可独立复现的业务场景为单位，可关联多个测试点；同一次操作产生的相关结果可一起断言。不同初态、操作或拒绝原因需分别执行时拆例，不将准备动作拆成用例，也不把同一操作后的每个展示字段拆成单独用例。
- 目录承载功能主线和共享场景，标题只写本分支的检查项，采用“功能点”或“功能点-区分项”，如“错误趋势展示”“搜索-跨资源域”“状态筛选-已办”。结合完整目录可辨认即可，不要求标题脱离目录独立表达对象、条件和结果。完整条件放前置，操作放步骤，判定放预期；标题不串联多个结果。同级标题平行且可区分；具体写法见 writing-style.md。
- 先列功能骨架，再展开场景和用例：菜单下先按实际页面或任务入口分组，同一级只采用一种分类口径。不得同时出现“新建/编辑/列表”与“列表与编辑”这类范围交叉的兄弟节点，也不得让同一功能在两个同级模块重复出现。跨页面场景按关键预期归入主要页面，其他页面写入步骤、标签与追踪；若各页面有独立结果则拆例。共享权限或数据状态只能放在明确页面/功能内部，除非产品本身存在独立的共享入口。
- 前置条件只写第一步之前必须成立的角色/权限、对象、状态和必要数据。按本例裁剪，不拼接全局夹具，不用“未指定时默认”“以下述场景为准”“每例独立重置”代替确定初态。数据建立方式可统一说明，但正式用例要包含执行所需的关键值和状态，不依赖上一用例或隐藏默认数据；确实无必要条件写 `pc: 无需`。
- 每条正式 XMind 用例只保留一个“操作步骤”主题；在该主题内用 `1. 2. 3.` 顺序写完入口、定位、输入、提交和回读动作。连续动作必须完整，不能缩成“设置后保存并回读”，但也不再把每次点击拆成多个步骤主题。前置已经到达的页面无需重复导航。
- 操作步骤主题下只保留一个关键预期主题，描述本例最终要判定的核心业务结果；过程中的页面到达、按钮可点、弹窗出现等仅在它们本身就是本例验证目标时写入关键预期。相关结果可用分号合并在同一主题，不为每个中间动作挂一个预期。不写“正常”“同上”“定位错误”或“符合要求”；保存后的回读必须先写成操作，再在关键预期中写可观察的字段、记录、状态或文案。
- `【】` 只用于界面按钮名称，例如“点击【保存草稿】按钮”；菜单、页面、页签、字段、筛选值和业务对象不得用 `【】` 强调，分别使用路径、普通文字或引号表达。
- 单因素反例只破坏目标条件，其他输入具体且有效；基准数据不能让发布例因缺环节/范围提前失败。负向结果按已确认契约描述，不一律假设拒绝且无副作用。并发、故障类明确参与者、注入位置、触发时点和观测方式；没有接口契约/工具时不伪造请求或将服务测试写成页面步骤。
- 只有 PRD、已确认原型说明、接口契约或批准规则明确规定字段的必填、长度、字符集/格式、数值范围/精度、枚举、唯一性、规范化或跨字段关系时，才建立对应的独立字段用例。没有特殊约束的普通字段只在创建、编辑等业务主流程中验证填写和保存，不额外生成空值、超长、中英文、特殊字符、类型或边界用例；不得从输入框类型、示例值、数据库类型或常识推导限制。明确约束的等价类和边界按 [reference/test-points.md](reference/test-points.md) 选取，不机械套齐所有字符类别或固定“三条用例”。
- 记录合适的测试层级（单元/接口/集成/E2E），在最低可充分验证层级设计；按风险考虑安全、性能、可访问性、兼容性与恢复性，不强制每个需求套用全部维度。
- `rc` 含稳定用例 ID、规则 ID、测试点 ID、模型项 ID 与依据位置；派生风险用例注明已确认设计/政策来源，不硬挂无关验收编号。模型项 ID 使用 `TP-001/B01` 等点内唯一标识。`rc` 中能力显示“中文能力名称（稳定能力 ID）”，需要时追加具体能力点，不能只输出 CAL.IDENTITY 等代码；发现能力粒度过粗或错配时修正受控字典及映射，不用名称美化掩盖错配。`tag` 包含本次交付版本（如 V0.1）、菜单、功能分组、层级和场景方向；版本来源于本次需求/计划，不硬编码为所有项目的 V0.1，也不将引入版本误当本次版本。验证成功路径或合法输入写“正向”；验证失败、拒绝、错误处理、权限拦截、非法/超长输入或阻止提交写“反向”；边界、等价类可作为附加标签，不能用“正向”覆盖反向场景。

## MeterSphere 大纲契约

- 第一个有效行是“测试用例”根节点；其下依次为“真实菜单路径 → 页面/任务入口 → 页面内功能 → 用例”，例如“测试用例 → 管理中心 → 规则配置 → 列表页面 → 状态操作 → 用例”。同一级目录使用同一分类口径，禁止范围重叠或重复主线；例如已经有“列表页面”“编辑页面”时，不再创建“列表与编辑”兄弟节点。跨页流程按关键预期归入一个主要页面。菜单与分组总深度最多8层，每级2个空格，不用 Tab。版本放tag与计划，不恢复“版本 → PRD名称”目录。台账分开保存 module_path（真实菜单）、function_path（功能分组）和 outline_path（最终目录）。
- 用例节点为 `tc-p0:` 至 `tc-p3:`；基础模式兼容无等级 `tc:`，正式交付须带等级。
- 用例标题默认只显示业务名称，不在标题中输出内部用例编号；生成器应提供布尔开关，默认关闭。稳定用例编号保留在 `rc` 用于追踪。
- 直接子节点为 `pc:`、`rc:`、`tag:` 和一个操作步骤主题。正式交付三个元数据节点各一个且非空，无子节点。
- 操作步骤主题在大纲中写为 `1. 第一个动作\n2. 第二个动作`，其中 `\n` 是同一主题内的换行标记；编号从1连续递增。该主题下恰好一个叶子主题，填写关键预期。标签用半角逗号。
- `#` 开头为注释，普通标题避免以 tc/pc/rc/tag 开头以免导入误判。
- 测试点与展开模型放 test-points.md，问题清单、风险表和追踪评审放 review.md，不混入导入大纲。

```text
测试用例
  顶部导航消息图标
    消息中心
      列表
        状态筛选
          tc-p1: 已办
            pc: 用户A已登录PC端；当前租户下发给用户A的待办类型消息只有两条：“订单甲待处理”为待办，“订单乙已完成”为已办。
            1. 点击顶部导航的消息图标，进入消息中心。\n2. 在待办页签点击【已办】按钮。\n3. 查看消息列表和筛选控件。
              列表只显示“订单乙已完成”，不显示“订单甲待处理”；不显示待阅类型筛选。
            rc: 用例 CASE-MSG-002；规则 RULE-MSG-029；测试点 TP-MSG-029；模型项 TP-MSG-029/M01；能力 入口与筛选（CAP-MSG-001）；依据 统一消息服务与消息中心 V0.1 PRD §4.1
            tag: V0.1,顶部导航消息图标,消息中心,列表,状态筛选,E2E,正向
```

示例来自消息中心的写法校准；其他项目需替换入口、规则、版本和编号，不能照搬业务预期。自动生成中间数据与文件时，还须遵守 [写作规范中的内容保真要求](reference/writing-style.md#生成工具的内容保真)。

## 交付门禁

- **菜单与资产评审**：逐级核对真实菜单前缀及来源；收起用例正文后，检查同级节点是否采用同一分类口径，是否出现“页面A / 页面B / 页面A与B”、同义名称或同一功能重复归属。跨页面用例必须能说明其唯一主要归属。核对每例版本tag及能力中文名称与字典一致；未映射项单列，不为凑齐目录猜测归属。增量场景核对稳定 ID、平台 ID、逐例决策、历史保留和计划按资产 ID 去重。构建器只验证结构，不能代替真实菜单核对。
- **执行可读性评审**：先按 [写作标准](reference/writing-style.md#交付前的执行推演) 推演每例的“前置→步骤→结果”，修正缺数据、跳步骤、无关前置、命名不清和目录难定位；抽样只能发现共性问题，不能代替最终逐例自检。
- **内容评审**：按 [测试点拆解参考的评审门禁](reference/test-points.md#5-内容评审门禁) 双向核对 PRD→规则→测试点→模型项→用例。追踪矩阵含规则 ID、测试点 ID、依据、测试条件/模型项 ID、用例 ID、风险/优先级、层级、设计覆盖状态及缺口原因。“已设计覆盖”不等于“执行通过”；引用编号不等于行为覆盖。所有范围内规则、测试点和适用模型项须关联用例或解释排除/阻塞原因；部分模型项未覆盖的测试点不得标成完整覆盖，高风险缺口突出展示。
- **结构与机械内容校验**：在本 skill 根目录运行 `python -X utf8 scripts/build_xmind.py --strict <outline.txt> <输出.xmind>`；从其他工作目录调用时使用该脚本的绝对路径。核对去重用例数与矩阵一致。严格模式检查字段、等级、单一操作步骤主题、动作编号连续、单一关键预期及明显占位预期，不验证业务正确性、目录语义或追踪完整性。
- **文件验证**：回读完整主题树及 ZIP 条目；`BUILD OK` 仅说明本地构建成功，不代表导入兼容。
