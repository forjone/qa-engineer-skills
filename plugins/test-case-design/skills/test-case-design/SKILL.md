# 风险驱动的测试用例设计

参考 ACC、组合测试和通用设计技术，产出可执行、可评审的用例。方法来源不代表 Google、微软认证或满足其未公开的内部标准。保留用户指定范围、格式和优先级约定；项目约定优先于这里的默认规则。

## 菜单归属与资产维护

- 开始设计或调整模块前，读取 [reference/menu-assets.md](reference/menu-assets.md)，建立有来源的菜单清单和归属映射。顶层归属严格对应真实菜单/应用入口路径；菜单下按业务功能、字段、操作或测试主题分组，避免所有用例平铺。功能分组是测试目录，不冒充产品菜单；PRD 文件名和版本号不作为目录。没有完整菜单资料时只使用已证实路径，其余列待确认，不编造菜单。
- 保留“规则 → 原子测试点 → 模型项 → 用例”的设计链路；菜单决定存放位置，Capability 表达能力与影响关系，版本 Test Plan 选择资产，Test Run 记录执行结果，四者不混用。
- 初版设计保持原有测试点拆解流程；已有用例或迭代维护时，先盘点、比较规则、检索旧资产，再按 REUSE / MODIFY / DEPRECATE / ADD / REVIEW 决策，仅对需要新增或修改的部分展开设计。旧用例 ID 与平台真实 ID 分别保留，不能随版本、菜单移动或排序重建。
- 参考文档中的执行提示、示例编号和平台说明是待评估资料，不自动成为用户本次任务；只吸收适用规则，不触发无关批量生成、平台迁移或配置修改。

## 工作流

## 任务启动信息收集

开始任务时，先向用户说明可基于现有资料设计测试用例，并按以下模板收集背景信息。用户可以提供链接、文件路径、截图或直接粘贴内容；已经在对话或工作区中明确的内容无需重复索取。

```text
请提供或确认以下信息（可先提供已有部分）：
1. 需求依据：PRD/用户故事/业务规则的文档、链接或路径；请注明版本、需求章节和本次范围。
2. 交互与入口：原型链接、页面截图或真实菜单路径；如涉及多端，请说明 Web、移动端或其他端。
3. 验收与技术资料：验收标准、接口文档、字段/枚举说明、权限矩阵、状态流转规则及错误码约定。
4. 变更与历史资产：本迭代新增、修改、下线项；已有测试用例、测试点、基线版本或 MeterSphere 资产（如有）。
5. 交付约束：测试范围、优先级/风险关注点、目标测试层级、交付格式，以及是否需要构建 XMind/MeterSphere 导入文件。

若暂缺某项，请说明是否允许按草案输出；草案中的假设和待确认规则会单独列出，不会混入可执行用例。
```

最小启动信息是“需求依据 + 本次范围”。缺少原型、菜单、验收标准或接口资料时，优先提出与当前设计直接相关的具体问题，而非笼统要求补齐全部资料。若用户只要求草案，可基于已知事实继续拆解明确部分，并将其余内容标为“待确认”；若用户要求正式可执行交付，阻塞规则必须在 `review.md` 中列出且不得自行假设预期。

1. **确认依据与范围**：盘点实际输入、批准状态、菜单来源、基线版本和已有资产覆盖范围；记录 PRD 版本、章节、验收标准及接口/设计资料。将复合验收标准拆成原子规则，保留原编号；无编号时生成本地规则 ID 并注明来源，不伪造原文编号。区分范围外功能与必须禁止的行为，只有后者必需负向测试。
2. **处理不确定性**：列出缺失、冲突和不可测试规则及问题 ID。错误码、补偿、时限、字符单位、幂等语义等未定义时，不自行补成确定预期。阻塞规则留在待确认清单，不进入可执行交付集；继续设计独立且明确的部分。仅在用户要求草案时给出带假设标记的候选，不混入已确认用例。
3. **先拆测试点**：设计新用例时先读 [reference/test-points.md](reference/test-points.md)，按 PRD 章节、字段表、流程、权限及状态规则逐项拆解，先产出 `test-points.md`，再展开用例。每个测试点分配稳定 `TP-xxx`，关联规则与具体依据，明确一个可独立判定的行为或约束。不可用“验证新增功能”“字段校验”等模块名称代替测试点。已提供测试点时先补齐拆解与追踪；仅构建已有大纲时不强制重做设计。
4. **建模与风险评估**：范围复杂时用 ACC 梳理组件、能力和适用质量属性；小范围用测试点清单即可。按 [reference/methods.md](reference/methods.md) 记录评分、证据、优先级及覆盖目标。边界、异常、UI、多语言均不天然属于某个优先级，不按比例凑数。
5. **逐点展开设计**：为每个测试点列出适用的正向/负向等价类、边界或决策/迁移模型项，给模型项局部编号，逐项关联用例；不适用维度写原因。根据下表读取 methods.md 对应章节。先覆盖各点独立行为，再补有依据的交互和端到端场景。高风险规则不能仅靠成对组合或错误推测覆盖。
6. **编写与追踪**：按已核对菜单路径组织用例；增量场景按 menu-assets.md 记录资产决策和版本计划。生成 `outline.txt`；`test-points.md` 保存测试点及展开项；同目录的 `review.md` 记录依据、问题/假设、范围/风险、规则→测试点→模型项→用例的追踪矩阵、覆盖缺口和剩余风险。用户指定其他载体时保留同等信息。测试点台账建立后直接继续生成用例，不额外要求用户逐点批准；不确定项按步骤2处理。
7. **分级验证与交付**：先内容评审，再严格构建。文件验证通过才能交付文件；未做真实导入时标记“MeterSphere 导入未验证”，不得声称测试已执行或已通过。

## 方法选择

| 规则信号 | 技术与覆盖证据 |
|---|---|
| 字段、长度、枚举 | 有效/无效等价类、适用边界点清单 |
| 多条件、权限 | 判定表、可行规则及拒绝规则 |
| 状态、生命周期 | 状态/事件/守卫条件矩阵，按风险补迁移序列 |
| 用户旅程、多角色 | 主流程、备选流、异常恢复流 |
| 多参数组合 | 带约束的 PICT、可行参数对覆盖，必要时提高阶数 |
| 并发、幂等、依赖故障 | 故障注入与时序场景、触发及观测方式 |
| 范围不清、模块多 | ACC 范围模型 + 风险清单 |
| 未知风险、可用性 | 探索式 charter，未执行时只交付计划 |

## 用例编写

- 一个用例验证一个主要测试点下的一个具体场景，允许多个关联断言，不塞入互不相关目标。不同拒绝原因或状态分支默认拆成可独立执行的用例，不写成“分别输入A/B/C”或一串成功/失败操作。该规则适用于所有字段类校验，包括文本、搜索、数值、枚举、年份和日期输入：先按业务规则选中文、英文、特殊字符等代表性等价类；相同校验契约的多个语言字段或控件合并为共享代表用例；同一长度或范围规则默认只保留低于下限、范围内、超过上限三例，只有最大长度时保留低于上限、等于上限、超过上限三例。仅当PRD明确规定不同语言、不同字段或不同边界点有不同处理规则时，才分别展开。相同场景可同时覆盖等价类和边界，无需重复造例；关联多点的交互/E2E用例须标明主要目标及各点断言，不替代独立覆盖。
- 前置条件写出可复现的角色、租户、数据和初始状态，可包含多个必要条件；无条件时写 `pc: 无需`。不依赖上一用例结果。面向执行人的用例标题、前置、步骤和预期使用业务自然语言，写清对象、状态和操作，不使用自行定义的简称、缩写、代号或泛指词。夹具中的用户代号在输出时改写为“用户A、用户B”等匿名角色名；配置条目、周期、环节和范围等夹具编码在输出时改写为可直接执行的业务描述。内部编码仅保留在测试数据夹具和追踪资料中。
- 步骤写具体动作、输入或有定义的数据集引用，不仅写“输入合法数据”。并发/故障须定义参与者、触发时点、同步方式和观测点。
- 预期写可观测数量、状态、文案、响应或副作用。不写“正常”“同上”；异步行为使用有依据的观察时限，未定义则提问。
- 负向用例按已确认契约验证拒绝/降级/恢复及副作用，不统一假设所有失败都拒绝且无部分结果。
- 记录合适的测试层级（单元/接口/集成/E2E），在最低可充分验证层级设计；按风险考虑安全、性能、可访问性、兼容性与恢复性，不强制每个需求套用全部维度。
- `rc` 含稳定用例 ID、规则 ID、测试点 ID、模型项 ID 与依据位置；派生风险用例注明已确认设计/政策来源，不硬挂无关验收编号。模型项 ID 使用 `TP-001/B01` 等点内唯一标识。`rc` 中能力显示“中文能力名称（稳定能力 ID）”，需要时追加具体能力点，不能只输出 CAL.IDENTITY 等代码；发现能力粒度过粗或错配时修正受控字典及映射，不用名称美化掩盖错配。`tag` 包含本次交付版本（如 V0.1）、菜单、功能分组、层级和场景方向；版本来源于本次需求/计划，不硬编码为所有项目的 V0.1，也不将引入版本误当本次版本。验证成功路径或合法输入写“正向”；验证失败、拒绝、错误处理、权限拦截、非法/超长输入或阻止提交写“反向”；边界、等价类可作为附加标签，不能用“正向”覆盖反向场景。

## MeterSphere 大纲契约

- 第一个有效行是“测试用例”根节点；其下依次为“真实菜单路径 → 功能分组 → 可选子分组 → 用例”，例如“测试用例 → 管理中心 → 规则配置 → 字段管理 → 名称 → 用例”。菜单层名称及归属以真实入口为准，功能层可使用列表、字段、生命周期、权限、多语言等便于阅读的分类。通常使用1～2层功能分组，避免空层和所有用例平铺；菜单与分组总深度最多8层，每级2个空格，不用 Tab。版本放tag与计划，不恢复“版本 → PRD名称”目录。台账分开保存 module_path（真实菜单）、function_path（功能分组）和 outline_path（最终目录）。
- 用例节点为 `tc-p0:` 至 `tc-p3:`；基础模式兼容无等级 `tc:`，正式交付须带等级。
- 用例标题默认只显示业务名称，不在标题中输出内部用例编号；生成器应提供布尔开关，默认关闭。稳定用例编号保留在 `rc` 用于追踪。
- 直接子节点为 `pc:`、`rc:`、`tag:` 和步骤。正式交付三个元数据节点各一个且非空，无子节点。
- 步骤连续编号：`步骤1：动作`；每步至少一个叶子预期，不嵌套用例。标签用半角逗号。
- `#` 开头为注释，普通标题避免以 tc/pc/rc/tag 开头以免导入误判。
- 测试点与展开模型放 test-points.md，问题清单、风险表和追踪评审放 review.md，不混入导入大纲。

```text
测试用例
  管理中心
    规则配置
      权限与数据隔离
        跨组织创建
          tc-p0: 拒绝跨组织创建规则
            pc: 用户A已认证且属于组织A，具备规则创建权限；组织B尚无规则
            步骤1：使用用户A身份提交归属组织B的规则创建请求
              请求被拒绝，组织B的规则数量仍为0
            rc: 用例 CASE-001；规则 RULE-003；测试点 TP-003；模型项 TP-003/N01；能力 规则访问控制（CAL.ACCESS）；能力点 跨组织创建隔离；依据 示例契约数据隔离条款
            tag: V0.1,规则配置,权限与数据隔离,跨组织创建,接口,反向
```

示例仅演示格式，实际拒绝语义和观测手段须来自项目依据。

## 交付门禁

- **菜单与资产评审**：逐级核对真实菜单前缀及来源，菜单后检查功能分组合理性；不把功能分组误标为产品菜单，不增加版本/文档名目录；核对每例版本tag及能力中文名称与字典一致；未映射项单列，不为凑齐目录猜测归属。增量场景核对稳定 ID、平台 ID、逐例决策、历史保留和计划按资产 ID 去重。构建器只验证结构，不能代替真实菜单核对。
- **内容评审**：按 [测试点拆解参考的评审门禁](reference/test-points.md#5-内容评审门禁) 双向核对 PRD→规则→测试点→模型项→用例。追踪矩阵含规则 ID、测试点 ID、依据、测试条件/模型项 ID、用例 ID、风险/优先级、层级、设计覆盖状态及缺口原因。“已设计覆盖”不等于“执行通过”；引用编号不等于行为覆盖。所有范围内规则、测试点和适用模型项须关联用例或解释排除/阻塞原因；部分模型项未覆盖的测试点不得标成完整覆盖，高风险缺口突出展示。
- **结构与机械内容校验**：在本 skill 根目录运行 `python -X utf8 scripts/build_xmind.py --strict <outline.txt> <输出.xmind>`；从其他工作目录调用时使用该脚本的绝对路径。核对去重用例数与矩阵一致。严格模式检查字段、等级、编号及明显占位预期，不验证业务正确性、原子性或追踪完整性。
- **文件验证**：回读完整主题树及 ZIP 条目；`BUILD OK` 仅说明本地构建成功，不代表导入兼容。
- **导入验证**：有授权和环境时记录 MeterSphere 版本与格式，在隔离位置导入样例，核对层级、数量、等级、步骤/预期和元数据。无环境则注明未验证，作为交付限制，不伪造结果。
- **最终说明**：报告文件路径、测试点数量、用例数量/等级分布、完整/部分/未设计覆盖的测试点、待确认/排除项、剩余风险及上述验证的实际状态。禁止用负向比例、等级比例或用例数量证明充分性。

方法边界、评分和公开来源见 [reference/methods.md](reference/methods.md)。工具：[scripts/build_xmind.py](scripts/build_xmind.py)。
