# 菜单模块与增量用例资产

## 1. 先确定菜单，再组织用例

读取用户提供的菜单导出、当前导航截图、原型和已批准 PRD 中明确的入口路径，记录版本与来源。材料冲突时列出冲突，不根据 PRD 章节或旧 XMind 推断真实菜单。截图若是用例树，只能证明旧分类，不能证明产品菜单。

建立 `module-map.md`（或等价表）：`旧路径 / module_path（真实菜单）/ function_path（功能分组）/ outline_path（最终目录）/ 菜单或入口类型 / 来源位置 / 关联资产ID / 状态 / 归属理由`。真实菜单部分名称、父子关系与产品一致；菜单后的功能分类可按业务规则规划，必须在台账标明为测试分组。菜单改名/移动时更新路径映射，保留资产 ID 与旧路径记录。

- module_path 是真实导航归属，function_path 是菜单内的功能分组，Capability 是稳定业务能力，三者不要求一对一。导入大纲使用 module_path + function_path；页面、字段、操作、状态等可形成有用的功能分组，通常1～2层，不把全部用例直接塞在菜单下。
- 每条用例只有一个主要归属菜单，可关联多个能力及需求。跨菜单场景按主要验证目标归属，其他入口写入关联关系；不复制同一资产到多个模块。
- 权限、多语言、异常、一致性、日志等检查分别归属其实际受测菜单，可以作为该菜单下的功能分组，并用标签/能力关联；不能提升为虚构的同级产品菜单。
- 没有菜单的后台服务或公共能力，记录为“无菜单能力/归属待确认”，保留设计与覆盖台账，不强挂某个菜单或静默遗漏。只有项目明确提供独立非菜单资产目录约定时才使用，并与真实菜单区分。
- 菜单不完整只阻塞未知路径的正式归属；继续处理有明确依据的部分。仅转换用户已有大纲时，不擅自重构原树，但报告其与菜单契约的差异。

### 虚构示例的局部映射依据

以下是用于说明目录组织的虚构 PRD 示例，不对应任何实际产品、菜单或项目；执行其他项目时必须以用户提供的真实入口路径替换。

```text
测试用例
  管理中心
    规则配置
      字段管理
        名称
          tc-pN: 对应名称字段的具体用例（示意，非可导入用例）
  应用工作台
    周期管理
      日期矩阵
        日期校验
          tc-pN: 对应日期校验的具体用例（示意，非可导入用例）
```

“周期管理”在此仅作为示意入口；应用工作台本身的发现/可见性行为归应用工作台，进入目标应用后的配置行为归周期管理。

| 旧截图分类 | 处理方式 |
|---|---|
| V0.1 / 示例规则与周期管理 | 移出版次和 PRD 名称目录；版本记录到计划/资产字段及每例tag（如V0.1） |
| 01 规则配置、02 字段管理、03 范围与顺序、04 规则生命周期 | 用例归管理中心 → 规则配置；菜单下保留字段管理、范围与顺序、生命周期等功能分组，并关联标签/能力 |
| 05 周期配置、06 周期主数据、07 日期矩阵、08 周期生命周期 | 周期配置用例归应用工作台 → 周期管理，下设周期配置、主数据、日期矩阵、生命周期等功能分组；后台同步服务本身按无菜单能力处理 |
| 09 异常与一致性、10 权限与数据隔离、11 多语言、12 通用交互、13 日志与跨模块 | 必须逐例按目标菜单拆分，在目标菜单下设置对应测试分组，不能按整个旧分支跨菜单直接移动；无菜单行为另记待归属 |

此表是迁移规则，不表示已完成现有文件或 MeterSphere 迁移。实际迁移需逐例保留 ID、统计移动/重复/未映射项并核对关联关系。

## 2. 资产与依据

每条资产保留 `asset_id, metersphere_case_id, module_path, function_path, outline_path, version_tags, capability_ids, capability_names, requirement_ids, source_refs, title, preconditions, steps, expected_results, priority, case_type, status`。平台 ID 未获得时留空并说明，不能伪造；新增本地 ID 先查重且保持稳定。建议另记首次引入/最近修改版本、回归级别、自动化状态、评审状态和变更原因。

Capability 字典包含 `id, name, parent_id, description, source_ref, status`，需要时加 owner。父子关系与跨模块依赖显式记录；能力 ID 不随名称或菜单排序变化，不为同义名称另建 ID。Requirement、Capability 和 Case 可多对多关联；不以这些关系取代测试点/模型项覆盖证据。rc 保留资产 ID、规则、测试点、模型项与来源；能力采用“中文名称（稳定ID）”，必要时另写具体能力点。中文名称来自字典，不能只显示代码。列表计数不能误挂仅负责创建复制的能力，需细分有独立规则的能力并记录映射调整。结构化台账另存平台 ID 和能力关系，不能假定 rc/tag 会自动转成平台关联字段。

确定预期优先采用已批准的本版 PRD/明确变更，再参考已批准基线、原型/契约与历史用例；不同资料冲突则记录问题，旧用例不得反过来覆盖明确新需求。来源必须能定位文件及章节/表格，示例不是业务事实。

## 3. 迭代决策

1. 盘点本版资料、批准状态、比较基线、旧库导出日期/范围、真实 ID 与平台模板。无基线时变化为 Unknown；无旧库时说明复用判断受限，不能报告“确认无可复用资产”。初版可以建立新库，不要求凭空补齐历史资料。
2. 原子规则对比标为 Added / Modified / Removed / Unchanged / Unknown，记录前后内容和依据。不能因新 PRD 未提及就认定旧规则删除。
3. 通过需求 ID、能力（含子能力）、依赖、业务对象、步骤和预期检索旧库；保留直接命中/子能力/需求关联/语义候选及理由，同一资产多路命中去重。语义相似只是候选，不能仅按标题判断复用或无影响。
4. 逐例记录下列决策，再对新增/修改的规则展开原子测试点和模型项；未变化用例复用已有设计和追踪，缺失信息则补全。

| 决策 | 条件与动作 |
|---|---|
| REUSE | 条件、行为和预期仍适用，引用原资产进入计划 |
| MODIFY | 同一行为的规则改变，保留原资产 ID、修改前后内容及原因 |
| ADD | 独立新行为或条件分支，查重后分配新 ID |
| DEPRECATE | 有明确移除依据，保留历史与追溯，不直接删除 |
| REVIEW | 证据不足、冲突或匹配不确定，列待确认，不自动废弃 |

长期并存且行为不同的版本可维护分支/变体，但不能按版本复制整库。已执行用例变更需保留修订或快照；操作平台前核实历史报告如何呈现用例内容。

5. 每例tag包含本次交付版本（如V0.1），版本必须有实际需求/计划依据；用version_tags记录该信息，与introduced_version、last_modified_version区分。版本计划引用资产 ID，New / Changed / Impact / Smoke 可重叠打标，总数按 ID 去重；不把 Deprecated 或阻塞预期作为已确认可执行集。区分候选计划和已落地计划。
6. 执行记录另存计划、环境、Build、日期、执行人和结果；设计覆盖不是执行通过。本地文件设计不等于已执行平台修改；平台动作按用户实际授权开展。

## 4. 按任务规模交付

简单新用例设计继续交付 `outline.txt`、`test-points.md`、`review.md` 与菜单映射，避免机械生成无意义空表。资产维护/迭代任务增加以下文件或同等章节：

- 输入盘点：版本基线、实际材料、缺失项及冲突。
- 需求差异：需求 ID、来源、旧/新规则、变化类型、问题。
- 能力字典及关系：稳定 ID、父子关系和依赖。
- 资产变更建议：decision、两类 ID、需求/能力、菜单路径、理由、来源、评审状态；MODIFY 附前后差异，ADD/MODIFY 附完整用例。
- 版本计划建议：范围、去重资产 ID、分组、优先级、进入/退出条件、待补环境/Build。
- 评审摘要：五类决策数量、测试点覆盖缺口、高风险和直接受变更影响的 P0/P1 开发自测清单。

可以沿用管理规范的 01～07 文件命名，也可合并进 review.md 并提供索引；不丢失信息、不维护互相矛盾的重复台账。缺资料须明确省略或受限原因。

XMind 是阅读/导入视图，结构化资产表保留稳定 ID 与多对多关系。未知 MeterSphere 版本、模板和字段支持时，只报告本地构建状态，不声称兼容或已导入。批量平台迁移前按实际授权做小样本验证，检查层级、真实 ID、等级、步骤/预期、自定义字段和关联关系；不将重新导入默认视作保留 ID 的移动操作。
