# 测试设计参考

评分与格式为项目默认约定，不是厂商标准。按需求选择技术，保存必要模型以支持评审；示例业务规则须经项目资料确认才可复用。

## 1. ACC 范围建模

ACC（Attributes、Components、Capabilities）见于 Google 测试相关公开著作《How Google Tests Software》。关联质量属性、组件与能力，筛选适用关系，不机械生成全部笛卡尔积。

输出组件/能力、适用属性、规则依据、风险和验证层级。将“安全”落到隔离、授权或敏感数据保护，将“稳定”转为明确的恢复契约。ACC 不保证覆盖完整，不是所有 Google 团队统一执行的标准。

## 2. 风险评分与优先级

风险用于分配测试深度/顺序，不等同缺陷严重程度。用例覆盖多个规则通常取最高适用优先级。已有团队尺度时记录其映射并使用。

默认相对评分，不把乘积解释为真实概率或期望损失：

| 分值 | 发生可能性 L | 影响 I |
|---|---|---|
| 1 | 有回归证据的稳定逻辑，变更/依赖影响小 | 可恢复的局部体验问题，不阻断任务 |
| 2 | 常规变更，存在分支或依赖；证据不足暂用此档并注明 | 部分任务受阻，有可行替代路径 |
| 3 | 相关缺陷历史或复杂变更，涉及并发/新依赖等高不确定性 | 核心流程阻断、不可逆数据损坏、重大资金/安全/合规后果 |

默认 R=L×I：6~9→p0，3~4→p1，2→p2，1→p3。重大安全/资金/合规或不可逆数据损坏默认提升p0，即使L较低；其他提升记录理由。核心能力不是自动p0，结合证据判断。

输出台账：规则 ID、L/I/R、证据或不确定性、最终等级、覆盖深度/理由。无历史数据不等于低风险。风险与需求变更后重新评审，不要求等级固定占比；边界/异常/多语言等按实际风险分级。

## 3. 等价类划分

按相同处理规则划分有效/无效类，记录范围、代表值和预期依据。单一无效因素用例用于定位；按风险补多无效因素的校验顺序或聚合错误场景。

Tenant缺失、超长、与认证身份不一致是不同条件；阈值和拒绝行为来自契约，不把所有非法输入合成一类。

## 4. 边界值分析

先明确有序域、开闭区间、单位与精度。整数闭区间可选min-1/min/min+1/max-1/max/max+1，去重并区分域外输入；连续值使用约定精度的邻点，不机械±1。

字符长度区分字节、码点、UTF-16单元或用户感知字符；时间考虑时区、精度和截止瞬间。未定义则提问。展示阈值99可测98/99/100，按规则补0/1和大值。输出边界、测试值、分区和预期依据。

## 5. 判定表

列出条件、取值、动作和可行性。仅全部布尔条件时组合数为2^n；多值条件按取值数乘积计算。

分析互斥、依赖与不可达组合。合并须证明省略条件不影响动作/副作用，不能只因结果文案相同就合并。可行决策规则关联用例；业务不允许但可提交的组合另测拒绝，不与无法构造组合混淆。

## 6. 状态迁移

提取状态、事件、守卫条件、动作/副作用与初态，记录状态×事件矩阵。覆盖适用合法迁移、可触发非法迁移及终态行为，幂等和拒绝不是任意互换的预期。

按风险补迁移对/序列（创建→撤销→更新）、重复/乱序事件、并发竞争、失败恢复。单次迁移覆盖不证明序列安全。记录可行迁移/序列与已设计数量、缺口理由，不把整个矩阵压成一个不可定位的用例。

## 7. 场景法与分层

覆盖主成功流、备选流和关键恢复流，步骤保留关联断言，数据可重置，失败可定位。

字段校验优先单元/接口；跨服务契约与补偿适合集成；关键旅程用E2E。注明环境、角色、数据、依赖控制和观测点，可在review.md按组记录。标明自动化候选和前提，不虚构已有自动化脚本。

## 8. 错误推测与故障时序

按缺陷历史、架构和依赖契约识别重复提交、超时、部分失败、重试、乱序及并发。设计含触发条件、数据、参与者/时序、注入位置、响应与持久化/外部副作用观测。

渠道超时区分发送前失败、远端成功但响应丢失；两者重复风险不同。补偿次数、截止时间和最终状态不明则待确认。错误推测不替代权限、判定规则和状态覆盖。

## 9. PICT 组合测试

微软开源工具PICT默认覆盖成对组合，也支持更高阶。覆盖对象为满足约束的可行参数对，不承诺全局最小用例数，不保证发现三因素以上交互缺陷。

以下模型只生成合法组合，假定即时通知不配置计划、定时通知必须配置计划，其余维度独立且均可行：

```text
NotificationMode: IMMEDIATE, SCHEDULED
Schedule: ONCE, RECURRING, NONE
Channel: EMAIL, WEBHOOK, IN_APP
Lang: zh-CN, zh-TW, en-US

IF [NotificationMode] = "IMMEDIATE" THEN [Schedule] = "NONE";
IF [NotificationMode] = "SCHEDULED" THEN [Schedule] <> "NONE";
```

命令：`pict model.txt > cases.tsv`。输出制表符分隔，记录版本、模型、约束、阶数和输出。高风险交互可用`/o:3`或额外场景；非法Type/SubType组合单独设计负向规则，不混入合法模型。

核验：根据完整约束确定可行完整赋值，投影全部可行参数对，比对生成行的参数对集合；同时检查每行满足约束。手工组合也须核验，未核验标“覆盖未验证”，不能凭观察宣称100%。每个组合仍需转为有操作和预期的用例。

## 10. 探索式测试与 SBTM

Session-Based Test Management源自James Bach与Jon Bach在惠普的实践，不是Google专属方法。探索可以在设计前、中、后开展。

计划明确charter、时间盒、范围、环境、风险和记录方式。执行记录含实际探索、证据、发现、阻塞与复盘；有价值回归检查补回用例。只生成计划不能声称已探索或已发现缺陷。

## 公开来源及边界

- ACC背景：《How Google Tests Software》，James A. Whittaker、Jason Arbon、Jeff Carollo，2012。历史公开方法，不作为现行统一标准或认证依据。
- [Software Engineering at Google：Testing Overview](https://abseil.io/resources/swe-book/html/ch11.html)：测试大小/范围、速度、确定性和持续验证，不把手工用例生成等同完整测试工程。
- [Microsoft PICT文档](https://github.com/microsoft/pict/blob/main/doc/pict.md)：模型、约束、组合阶数。
- [SBTM原始介绍](https://www.satisfice.com/download/session-based-test-management)：来源和会话管理。
- 等价类、边界值、判定表、状态迁移与风险驱动属于通用实践，可对照[ISTQB CTFL](https://www.istqb.org/certifications/certified-tester-foundation-level)公开大纲，这里不宣称经过认证。

本skill约束设计与交付，测试充分性仍需结合架构、历史缺陷、执行结果和剩余风险评审。
