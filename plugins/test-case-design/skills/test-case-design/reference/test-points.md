# 从 PRD 原子测试点到可执行用例

## 1. 原子测试点的拆解尺度

区分三层：规则是需求依据；测试点是一个可独立判定的行为或约束；用例是验证该点的一组确定条件、输入、动作和预期。一个规则可拆多个点，一个点通常展开多个用例。不要把每个数据值都命名为新测试点，也不要把模块直接当测试点。

逐节提取 PRD 中的“必须、仅、当、否则、最多、至少、默认、不可、失败后”等约束，同时检查字段表、图中分支、脚注和验收标准。相同规则跨章节重复出现时合并依据，冲突则记问题；不能仅按目录标题生成覆盖清单。

按实际需求检查这些拆分轴，不强制补没有依据的功能：

| 对象 | 可以独立拆出的点 |
|---|---|
| 字段 | 必填、类型/格式、长度上下限、枚举、默认值、唯一性、规范化各自独立 |
| 动作 | 可见性、可操作条件、操作结果、可独立失效的持久化/通知等副作用 |
| 权限 | 角色对具体动作的权限、数据归属/租户隔离、字段读写权限 |
| 状态 | 每条有业务差异的迁移、守卫条件、可触发的禁止迁移 |
| 计算/查询 | 计算分支、精度/舍入、筛选语义、排序规则、分页边界 |
| 流程/依赖 | 主分支、备选分支、已定义的失败处理、重试/恢复/幂等语义 |

拆分判断：若一个点包含的两个行为能独立失败、预期依据不同，或需要不同的前置状态/动作才能判断，应拆开。上下限可分别成点，尤其处理不同或需独立追踪时；一个简单闭区间约束也可保留为一个点，并完整列出两端边界。一个操作后的响应与一致性检查可留作关联断言；独立通知规则则另设点，原场景仍可检查通知。

禁止为追求细度将“打开页面”“点击按钮”等准备动作各拆成测试点，除非其本身有明确待验证行为。复杂条件规则保留判定表，不能拆掉条件间关系。

## 2. 先建立测试点台账

`test-points.md` 至少包含下列信息，可按模块分表：

| 测试点 ID | 规则 ID / 具体依据 | 原子验证目标 | 适用条件与可观察判定 | 风险/优先级 | 状态/问题 ID |
|---|---|---|---|---|---|
| TP-001 | RULE-001 / PRD §2 数量字段 | 数量不得小于1 | 授权用户提交整数数量，小于1拒绝且不创建记录 | 引用风险台账 | 已明确 |

这里的业务描述仅为示例，不作为真实项目默认规则。依据要定位到章节/字段/表格行，必要时附短摘录。稳定 ID 不随排序改变；新增点追加 ID。明确规则与推导风险点分开标注，未确认预期的点保留问题 ID，不能凭常识补错误码、提示语或数据副作用。

台账后列各点的展开项：`测试点 ID / 模型项 ID / 维度 / 分区或条件 / 代表输入 / 预期依据 / 用例 ID 或缺口原因`。ID 可使用 P01（正向）、N01（负向）、B01（边界）、D01（决策）、S01（迁移）等；维度允许多标签，不要求固定前缀。

## 3. 逐点展开，不机械凑正反例

1. **确定基准场景**：先定义角色、状态、其他字段均有效的基准数据，让待测因素能真正到达目标校验。用具体值或同目录定义完整的数据集，不留“合法数据”占位。
2. **划分等价类**：按处理规则分有效/无效类，每个有不同处理路径的类至少选一个代表。缺失、null、空串、纯空格、类型错误只有契约区分时才分别确定预期；未说明的区别记问题或风险候选。枚举值有独立业务行为时分别覆盖，不能抽一个代表全部。
3. **列出边界**：明确单位、精度、开闭区间和可表示输入，使用端点及相邻可达值；整数常用下界−1/下界/下界+1及上界−1/上界/上界+1。窄区间去重；时间/金额/字符不机械±1。不适用有序域时写“不适用：无有序阈值”。
4. **覆盖条件与状态**：为适用判定表的可行决策、状态迁移和拒绝分支逐项选场景。主成功路径不能代表所有合法分支，一条失败路径不能代表所有拒绝原因。
5. **隔离负向因素**：单因素反例中只违反目标约束，其他因素保持有效；权限用例须能通过认证，长度反例须满足格式等其他要求。无法隔离时说明耦合与实际能观测的规则，不冒称两个校验都已覆盖。
6. **补交互**：完成独立点后，按依赖关系与风险补跨字段约束、校验顺序、多条件、重复/并发和恢复场景。组合需有明确依据与预期；不对所有输入做笛卡尔积，也不以成对组合替代单点边界。
7. **去重并落地**：每个保留的具体输入/分支生成独立用例，便于重跑和定位。一个值同时命中有效类与边界时复用同一用例并关联全部模型项；相同预期但触发不同规则的反例不能仅因文案相同合并。用户明确要求参数化时，每一行仍须有独立数据、预期和追踪标识；输出 XMind 时默认展开成独立节点。

逐点评估正向、负向、边界、条件/状态和交互是否适用，记录适用项或简短不适用原因，可对相同原因按点组记录。纯展示点可验证显示内容、显示条件和无数据状态，不为凑反例发明拒绝操作。边界与等价类是可重叠设计技术，不是互斥用例类型。

## 4. 示例：一个字段不能只写一条“校验数量”

假设 PRD 明确：已授权用户提交数量时，数量必填、必须是 JSON 整数，范围1～100；缺失、null或非整数均拒绝；合法请求创建一条记录，非法请求不创建记录。其他字段固定有效。不假定未定义的错误码或提示文案。

拆为：TP-101 必填约束（缺失/null）、TP-102 JSON整数类型约束、TP-103 最小值1、TP-104 最大值100。合法提交的创建行为可另设 TP-105，并用同一成功场景关联验证。

| 点/模型项 | 输入 | 设计意图 | 预期 | 对应用例 |
|---|---|---|---|---|
| TP-101/P01、TP-102/P01、TP-103/P01、TP-104/P01、TP-105/P01 | 50 | 正向代表，关联断言分别记录 | 创建一条记录，保存数量50 | CASE-101 |
| TP-101/N01 | 请求中省略数量字段 | 必填无效类 | 拒绝，不创建记录 | CASE-102 |
| TP-101/N02 | null | 契约明确的空值反例 | 拒绝，不创建记录 | CASE-103 |
| TP-102/N01 | JSON字符串 "50" | 字符串类型无效类 | 拒绝，不创建记录 | CASE-104 |
| TP-102/N02 | 1.5 | 非整数数值无效类 | 拒绝，不创建记录 | CASE-105 |
| TP-102/N03 | true | 布尔类型无效类 | 拒绝，不创建记录 | CASE-106 |
| TP-102/N04 | [] | 数组类型无效类 | 拒绝，不创建记录 | CASE-107 |
| TP-102/N05 | {} | 对象类型无效类 | 拒绝，不创建记录 | CASE-108 |
| TP-103/B01 | 0 | 下界外邻点、无效类代表 | 拒绝，不创建记录 | CASE-109 |
| TP-103/B02 | 1 | 下界 | 创建一条记录，保存数量1 | CASE-110 |
| TP-103/B03 | 2 | 下界内邻点 | 创建一条记录，保存数量2 | CASE-111 |
| TP-104/B01 | 99 | 上界内邻点 | 创建一条记录，保存数量99 | CASE-112 |
| TP-104/B02 | 100 | 上界 | 创建一条记录，保存数量100 | CASE-113 |
| TP-104/B03 | 101 | 上界外邻点、无效类代表 | 拒绝，不创建记录 | CASE-114 |

此表是展开模型，实际用例还要补齐独立前置、具体操作和可观察断言。CASE-101 的主目标为 TP-105，复用其对必填/类型/范围的正向覆盖须有相应输入与保存值证据。非法用例各自使用全新的有效基准，不依赖上条用例。缺失/null归必填，避免同时制造类型失败；0/101归边界且兼作无效类代表，避免另复制等价类用例。这里不预设所有规则共用一个错误消息。

## 5. 内容评审门禁

- **从需求查遗漏**：PRD 每条范围内规则均落到测试点或有明确排除/问题原因；特别核查“否则”、默认、禁止和失败后分支。
- **从点查颗粒度**：名称含多个独立行为、多个字段校验或整段旅程时，重新做拆分判断；检查拆分后是否遗失交互规则。
- **从模型查覆盖**：每个适用分区、边界点、决策项、迁移项均能定位用例或缺口；有一个正向用例不能将整个点标为完整覆盖。
- **从用例查有效性**：追踪能反向定位依据；输入确实命中目标模型项，前置不拦截目标路径，反例不被其他无效因素掩盖，预期不超出已确认契约。
- **查独立性与冗余**：不同数据/分支能独立执行；多点用例有明确主目标和逐点断言；边界/等价类重合场景已去重，不因总数目标缩减或灌水。
- **报告真实缺口**：按“完整设计覆盖、部分设计覆盖、未设计覆盖、待确认、排除”记录测试点状态。完整表示全部已识别且适用的模型项有可执行用例，不表示穷尽缺陷；报告数量时说明分母与排除范围。
