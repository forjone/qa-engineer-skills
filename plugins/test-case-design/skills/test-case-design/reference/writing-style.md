# 用执行人的语言写用例

本规范从用户历史手写用例中的有效写法归纳：按产品页面定位、按控件和操作分组、标题直接描述行为、步骤写清进入菜单和点击对象、前置只保留场景需要的数据。它是默认写作风格，不是固定句式或步数配额。用户有新的明确约定时优先采用。

## 1. 结构：功能主线 → 场景分组 → 检查项

默认按用户示例的树形阅读方式设计：上层说明测哪个功能，必要的中间层说明共享场景，叶子用例点明检查项。先看收起步骤/预期后的树，能辨认展示、搜索、操作等主线，再编写正文。规则/测试点台账用于查覆盖，不直接变成阅读目录。

用户截图中的有效组织方式（仅作写法参考，不是当前产品菜单依据）：

```text
错误分析
  有权限
    tc-p1: 错误趋势展示
    tc-p1: 错误请求趋势展示
    tc-p1: 按错误原因查看-结果展示
    tc-p1: 按服务实例查看-结果展示
    tc-p1: 搜索
    tc-p1: 搜索-跨资源域
  无权限
    tc-p1: 页面展示
    tc-p1: 通过链接访问
```

- 真实菜单或入口保留在上层；之后先按页面或任务入口分组，再按页面内功能分组。同一级只能使用一种分类口径：已有“新建页面、编辑页面、列表页面”时，不得再增加“列表与编辑”“通用页面”等范围交叉的兄弟节点。截图的“有权限/无权限”是测试分组，不冒充产品菜单。
- 同级采用同一分类逻辑。一个功能内共享条件明显且用例较多时，可以设“有权限/无权限”“草稿/已发布”等场景组；否则用短后缀区分，避免为每条用例造单子目录。
- 功能骨架先覆盖本次明确范围的主要行为，再在各主线内补异常、边界、权限等变化。目录要让人看清功能，不要只剩一堆零碎的字段边界和结果断言。
- 深度由检索价值决定，不强制1～2层，也不为每个条件都加一层；仍遵守导入的总深度限制。同一主场景只存一份，关联能力放追踪信息。跨页面用例按最终关键预期选择唯一主要页面；如果两个页面各有独立判定目标，拆成两条用例。
- 当一个长标题包含多个独立功能，先判断是否应拆例；同一次操作的关联结果可留在同例预期，标题只取主检查项，不必列完所有断言。

## 2. 名称：短检查项，不写成验收句

标题和目录一起阅读。默认使用“功能点”或“功能点-区分项”。`【】` 只表示界面按钮名称，不表示关键控件，也不用于强调文字。菜单、页面、页签、字段、筛选值和业务对象不用 `【】`。不要强制“对象+条件+操作+结果”齐全，也不要要求离开目录仍能理解。一般用短语而非整句，不设硬字数上限、不机械截断。

| 目录上下文 | 用例标题 | 正文承担的信息 |
|---|---|---|
| 消息中心 → 待办列表 | 默认展示 | 默认页签和状态的具体预期 |
| 消息中心 → 待办列表 | 状态筛选-已办 | 已办/待办对照记录与筛选结果 |
| 消息中心 → 待阅列表 | 类型筛选-主动通知 | 通知类型数据、筛选结果及页签计数 |
| 商品日历 → 新建日历 | 空白新建 | 环节范围为空、未编辑返回不落草稿 |
| 商品日历 → 新建日历 | 复制-沿用原名 | 原日历状态、保存操作与重名提示 |
| 商品日历 → 编辑日历 → 日历名称 | 长度上限 | 100字符输入、保存及回读 |
| 商品日历 → 编辑日历 → 日历名称 | 重名-已停用日历 | 同租户和已停用记录、重复保存被拒绝 |
| 错误分析 → 无权限 | 页面展示 | 无权限角色和应显示的提示/受限内容 |

- “展示”“搜索”在明确功能/场景分支下可以是合格标题；同一分支有多个展示区时，应写“错误趋势展示”“错误请求趋势展示”来区分。不能一律禁用这些手写风格的短名称。
- 不把整条预期塞进标题，不把“并且、同时、仍然”等多个断言串在一起。“类型筛选-主动通知”不需要再接“只显示主动待阅且计数仍包含订阅”。
- 同级不同场景不能同名。长度有多个例时可用“长度-99字符 / 长度-100字符 / 长度-101字符”，或“未达上限 / 长度上限 / 超出上限”；同组保持一种形式。数值只有对区分场景有用时才进标题，精确输入仍放步骤。
- 目录已包含的功能对象不反复抄进每个标题；共有场景也不在标题重复。不把模型编号、长夹具名和追踪信息写入名称。
- 搜索或导出为扁平列表时展示“目录路径 + 短标题”以保留上下文；不要为了扁平视图反过来拉长树上的标题。用例正文仍须可独立执行，目录分组不能代替pc中的真实权限/状态。

## 3. 前置：足够复现，不是整个环境说明

只保留会影响第一步执行或结果的事实。先在草稿中列出环境、角色、数据、状态，再逐项问“删掉它，执行人还能准备正确场景吗？”能且不影响判断的就删除。

**保留**：操作人必要权限、目标对象名称与初态、关键关联、需要对照的记录及数量、当前语言/租户（与目标相关时）、故障注入的环境能力。

**移出**：测试策略、每例重置的口号、观测方法、未使用的其他用户/品牌、整个功能的所有基准字段。观测动作放步骤；公共环境建立方式可放测试准备说明。

**不得省略**：步骤引用的数据、导致分支的状态、排除其他失败的必要条件。不要用“均合法”“按默认值”“对象状态以下述场景为准”掩盖缺数据。若使用独立数据文件，交付它并写明记录位置；导入用例仍展开关键值和状态，不依赖目录父节点隐式继承。

例如，筛选“已办”只需要当前用户有一条已办和一条待办；不需要为每例再定义跨租户用户、消息摘要和跳转地址。权限隔离用例则必须明确两个用户或租户各自的数据。

“准备完成的状态”和“本例正在验证的动作”分开：验证发布时，前置可有未发布草稿，不能预先写已发布；验证创建时，不能先把目标对象创建完成。使用现存记录是合法前置，但要明确它的必要字段和状态，不能依赖前一个测试刚创建。

## 4. 步骤：一个操作块走到关键结果

按执行顺序写：进入入口 → 定位对象 → 输入/操作 → 提交 → 到明确位置检查结果。正式 XMind 中，这些动作合并在一个主题内，用 `1. 2. 3.` 编号和换行组织；主题下只挂一个关键预期。这样执行链完整，但不会在脑图上展开成大量零碎的步骤/预期分支。

- “点击【保存草稿】按钮”比“进行保存验证”直接；“返回商品日历列表，打开‘春季商品计划’，查看‘简体中文名称’字段”比“回读一致”可执行。
- 导航、填写、保存、弹窗确认、刷新和重新进入按先后写成操作块内的独立编号；不为了凑数量拆鼠标动作，也不能遗漏确认或回读。
- 关键预期只写本例最终业务判定。中间页面到达、按钮状态和弹窗出现仅在其本身是本例目标时保留；其他过程结果由后续动作已经可达这一事实承接，不再逐项挂预期。
- 先确认输入在该层级可达：控件已阻止超长输入时，UI验证阻止输入；需要验证服务端拒绝则另用已定义接口，不能绕过控件后仍称纯人工页面用例。资料未明确拦截时机时记录缺口，不编造即时提示或提交拒绝。
- 输入应有具体值。ASCII长度测试可用“连续输入101个大写字母A”精确表示；带复杂 Unicode 的长度测试需确认计数单位，不把ASCII样例当成中文/组合字符覆盖。
- 只有按钮名称使用 `【】`，例如“点击【保存草稿】按钮”。菜单写“进入配置中心 > 商品日历”，页面写“进入商品日历编辑页”，页签写“切换到待办页签”，字段写“在‘简体中文名称’字段输入……”，筛选值写“选择‘已办’”。仅对已知真实名称使用精确称谓；资料只说“选择年份”时不发明按钮位置或入口。
- UI场景检查UI可见事实；接口场景写有依据的请求和响应；服务集成场景给触发、注入与观测方法。层级不同不能共用“进入页面后查看请求记录”的万能模板。缺接口定义的业务规则可先保留设计点，但不得声称请求步骤已经可执行。
- 同一场景的相关关键结果可用分号写在一个预期主题中。不同输入的成功/失败试验默认独立用例；参数化仅在用户约定或工具支持时使用，每组仍有明确输入和预期。

## 5. 正反例：不是只把句子写长

以下两例都位于“消息中心 → 待办列表”分支，标题依赖此上下文；正式大纲必须保留目录。

旧生成例“全局入口默认待办待办”：前置堆叠三个用户和消息模板，步骤只有“从顶部导航消息图标进入”。改为：

```text
tc-p1: 默认展示
  pc: 用户A已登录PC端，具有消息中心访问权限。
  1. 点击顶部导航的消息图标，进入消息中心。\n2. 查看页签和筛选控件。
    显示待办和待阅两个一级页签；默认选中待办页签，状态筛选值为“待办”。
```

这条无需把两个动作拆成多个步骤主题；去掉无关条件并明确关键结果就足够。示例省略rc/tag，正式大纲必须补齐来源与追踪。

旧生成例“已办筛选只显示已完成待办”：前置只说“存在有效待办和已办”，改为以下可核对数据：

```text
tc-p1: 状态筛选-已办
  pc: 用户A已登录PC端；当前租户下发给用户A的待办类型消息只有两条：“订单甲待处理”为待办，“订单乙已完成”为已办。
  1. 点击顶部导航的消息图标，进入消息中心。\n2. 在待办页签点击【已办】按钮。\n3. 查看列表和筛选控件。
    列表只显示“订单乙已完成”，不显示“订单甲待处理”；不显示待阅类型筛选。
```

这里的记录名是可自行准备的测试数据，不是产品预置事实。正式使用前必须核对本项目的入口、筛选和状态规则。反例：只把“一步切换已办”拆成“进入页面/点击/检查正常”仍然不合格，缺的对照数据与确定结果没有解决。

## 生成工具的内容保真

生成器只负责序列化经过评审的用例，不负责用全局模板补齐语义。

- 中间数据可以保留细分动作，生成正式 XMind 时必须按原顺序合并成一个编号操作块；从所有过程预期中提炼一个有依据的关键预期，不能简单丢弃最后一步之前的核心断言，也不能把每个过程预期继续输出为独立节点。
- 前置逐例显式编写。公共数据可以复用定义，但应按该例依赖挑选并展开；不要采用 `BASE[模块] + 场景补充` 无条件拼接。碰到冲突初态时修数据，不能追加“以下述为准”覆盖。
- Markdown、大纲和XMind从同一份已评审内容生成；构建后抽查标题、前置、编号操作块与关键预期是否完整保留。现成项目脚本若会丢失动作、保留多组碎片预期或覆盖已修改内容，先修其数据模型和输出逻辑；不得直接重跑旧脚本污染新产物。
- 不根据字数、步数、关键词或重复率自动判定业务合格；它们只能帮助发现需要复核的用例。

## 交付前的执行推演

逐例从初态向后推演，记录发现的问题并修正。以下任一项不满足，不能用“已构建”掩盖：

1. **结构**：收起步骤和预期后能看清功能主线、场景分组与检查项吗？同级分类是否重叠，归属依据是否成立？
2. **名称**：结合目录能认出本例检查项和与相邻用例的差异吗？有没有重复父节点、塞入完整条件或多个结果？允许“页面展示”“搜索”等上下文明确的短标题。
3. **前置**：所有用到的对象、关键数据和初态都有定义吗？是否包含无关条件，或把被测结果提前成立？
4. **步骤**：从前置开始，每一步都能到达下一步吗？入口、输入、提交、确认、返回检查有没有缺失？反例是否只改变目标因素？
5. **判定**：关键预期是否在完整操作链执行后可观察、可比较且有需求依据？有没有遗漏回读动作，或把中间过程结果当成最终关键预期？
6. **覆盖**：优化表达或合并相关断言后，原有效分支/边界是否仍有明确输入与断言？不能为了像手写而删掉关键覆盖。

可记录每项“通过 / 需修正 / 资料阻塞”及具体证据，不设字数、步骤数、平均长度或用例总数达标线。机械工具仅检查结构；语义质量依赖上述推演。
